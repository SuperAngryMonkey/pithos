# Pithos v0.5.0 Release Notes

**VM provisioning.** The VM templates listed in v0.4.0 can now actually be
cloned. Selecting one in the picker provisions a virtual machine instead of a
container.

## Why a second script

The LXC path clones with `pct` and injects the Tailscale key with `pct exec`.
Neither works for a VM, so `pithos-new-vm` clones with `qm` and hands the key
over through a cloud-init drive, which Cloudbase-Init (Windows) or cloud-init
(Linux) consumes on first boot. Everything else is shared: the same OAuth
client mints the key, the same VMID and onboot handling applies.

## What happens on a VM clone

1. A single-use, short-lived, pre-authorized auth key is minted per clone.
   A key baked into a template would let any copy of the image join the tailnet.
2. User-data is written to a snippet: join the tailnet, rename the machine,
   restart. That order matters - Windows only applies a rename on restart, and
   the tailnet session survives it because the service runs unattended.
3. `qm clone --full`, then cloud-init user/password/IP and `--cicustom`.
4. Start, and wait for the guest agent to report the new hostname.

Provisioning finishes with a **restart**, so the VM disappears briefly at the
end. That is expected, not a failure.

## Requirements

- `snippets` content enabled on a storage (`pvesm set local --content ...,snippets`)
- A VM template whose guest runs Cloudbase-Init or cloud-init
- Tailscale OAuth credentials, as for LXC provisioning
