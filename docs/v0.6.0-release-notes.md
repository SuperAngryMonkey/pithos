# Pithos v0.6.0 Release Notes

**Network selection.** Clones are now placed on a chosen bridge instead of
silently inheriting the template's.

## Why this is a safety fix, not a convenience

`pithos-new` set no network configuration at all, so a clone kept whatever
bridge its template carried. On a host whose `vmbr0` holds a public address —
as is the case for an internet-facing node — cloning a template bound to
`vmbr0` puts a brand new guest straight onto the internet with a routable
address, with no indication that this is what happened.

## What's new

- **Bridge enumeration**, each with its CIDR and a `public` flag. Anything
  outside RFC1918, loopback, link-local and CGNAT counts as public.
- **`GET /api/bridges`** for the MCP and scripted clients.
- **A NETWORK picker** in the clone form showing each bridge's address, with
  public ones labelled `- PUBLIC`. The first private bridge is preselected.
- **`--bridge <name>`** on both `pithos-new` and `pithos-new-vm`, applied after
  the clone so placement is explicit.
- Server-side validation against the host's real bridge list.

Leaving the bridge unset still inherits the template's, so existing scripted
callers are unaffected.

## Notes

Two things worth knowing if you extend this: `ip -4 -o addr show type bridge`
does not reliably filter by type on every iproute2 build, so the bridge list is
taken from `ip -o link show type bridge` and addresses attached afterwards; and
some Python versions do not treat CGNAT (100.64.0.0/10) as private, which would
mark a tailnet interface as public, so that range is special-cased.

## Files changed

- `webui/app.py` — enumeration, `/api/bridges`, picker, validation
- `scripts/pithos-new.sh`, `scripts/pithos-new-vm.sh` — `--bridge`
